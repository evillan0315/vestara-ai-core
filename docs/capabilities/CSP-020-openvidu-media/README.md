# CSP-020 — OpenVidu Media Integration

**Objective**: Integrate OpenVidu WebRTC media into Activity Room, enabling live video/audio conferencing with voice-to-agent intelligence.

**Server**: `https://viduk.swinglifestyle.com` (OpenVidu 2.25.0)

**Status**: OVR-000–OVR-007 frozen. OVR-008 implementation complete (live acceptance blocked/indeterminate). OVR-009A–009B frozen. OVR-009C not started.

**Control plane authority** uses the **native OpenVidu 2.25 REST API**, not the partial `/api/...` application-server layer.

```
Control plane authority

https://viduk.swinglifestyle.com
        │
        └── /openvidu/api
                │
                ├── POST /sessions
                │
                └── POST /sessions/{id}/connection
```

The `/api/sessions` endpoint is an existing deployment-specific application endpoint. It is documented but **not the foundation of `openvidu-runtime`**. Having one operation work there while connection creation returns 404 is exactly the kind of partial abstraction that becomes troublesome later.

## Provider-Neutral Contracts

OpenVidu's `Session` and `Connection` classes are **not** Vestara domain objects. They are provider implementation details behind the `MediaServer` port.

```ts
interface MediaSession {
  id: string;
  provider: "openvidu";
  externalSessionId: string;

  status:
    | "creating"
    | "active"
    | "closing"
    | "closed"
    | "failed";

  createdAt: number;
}

interface MediaConnection {
  id: string;
  sessionId: string;
  externalConnectionId: string;

  role:
    | "subscriber"
    | "publisher"
    | "moderator";

  status:
    | "pending"
    | "active"
    | "disconnected";

  token?: MediaConnectionToken;
}

interface MediaConnectionToken {
  value: string;
  expiresAt?: number;
}
```

**Connection tokens are capability-bearing ephemeral material, not ordinary metadata.** They must not be persisted into Activity Room events, evidence, logs, or normal API traces.

## Configuration

```text
OPENVIDU_URL=https://viduk.swinglifestyle.com
OPENVIDU_API_BASE=/openvidu/api
OPENVIDU_USERNAME=OPENVIDUAPP
OPENVIDU_SECRET=<secret-reference>
```

**Not:**

```text
OPENVIDU_WS_URL=wss://...
```

Signaling details belong to the connection token/runtime. The WebSocket URL is generated by OpenVidu inside the connection token.

## Constraints

1. **Do not modify the VidUK server**, webhook configuration, or existing conferencing deployment
2. **Do not modify Activity Room** until OVR-003/OVR-004 proof passes
3. **Do not modify Voice Runtime** until OVR-007/OVR-008 audio observation is proven
4. **Do not expose OpenVidu classes** as Vestara domain objects
5. **Do not persist connection tokens** into events, evidence, or logs
6. **Do not silently take over the webhook** at `chatv.swinglifestyle.com`
7. **Build and prove the Vestara media boundary first** — then integrate into Activity Room

**OVR-004 proof** (2026-09-05): Two headless Chromium browsers connected to a disposable session on VidUK. Browser A published fake video (Pac-Man test pattern). Browser B subscribed and received the stream. Provider confirmed both connections active. Full cleanup completed. Evidence: `OVR-004-evidence-ovr004-*.json`.

Once that works independently, integrating into Activity Room becomes a UI/projection problem rather than simultaneously debugging authentication, REST contracts, signaling, ICE, WebRTC, React, and Activity Room.
