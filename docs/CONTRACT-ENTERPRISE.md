# Enterprise Contracts

Governance model for organizational behavior within the Vestara platform.

---

## Organization

```typescript
interface Organization {
  id: string;
  name: string;
  description: string;
  repositories: OrganizationRepository[];
  createdAt: string;
  updatedAt: string;
}
```

**Invariants:**
- An Organization owns zero or more Repositories.
- An Organization has exactly one name.
- Repositories can belong to exactly one Organization at a time.
- The Organization is the root aggregate for enterprise governance.

**Source:** `packages/workspace/src/types.ts`

---

## Team

```typescript
interface Team {
  id: string;
  name: string;
  description: string;
  members: string[];
  role: 'admin' | 'engineer' | 'viewer';
  createdAt: string;
}
```

**Invariants:**
- A Team has exactly one role.
- Members are referenced by user ID (string).
- Teams are flat (no nested teams in v1).
- Roles determine default permissions within the Organization.

**Evaluation model:** Role-based. `admin` inherits all permissions. `engineer` can create/modify artifacts. `viewer` is read-only.

**Source:** `packages/workspace/src/types.ts`

## Project

```typescript
interface EnterpriseProject {
  id: string;
  name: string;
  goal: string;
  repositories: string[];
  status: 'active' | 'archived';
  createdAt: string;
}
```

**Invariants:**
- A Project has a goal (engineering objective).
- A Project references zero or more Repository paths.
- A Project can be archived but not deleted (immutable history).
- Archived projects are read-only.

**Source:** `packages/workspace/src/types.ts`

## ApprovalPolicy

```typescript
interface ApprovalPolicy {
  id: string;
  name: string;
  artifactType: 'plan' | 'changeset' | 'verification';
  requiredApprovers: number;
  roles: string[];
  createdAt: string;
}
```

**Evaluation model:**
1. Load the policy matching the artifact type.
2. Check if the requesting user's role is in `roles`.
3. Verify that the number of approvals on the artifact meets `requiredApprovers`.
4. If all conditions are met, the artifact is considered approved.

**Invariants:**
- Policies are additive (default-deny if no policy matches).
- `requiredApprovers` must be ≥ 1.
- `roles` must contain at least one role.
- Policies cannot be deleted, only superseded by newer versions.

**Default policies seeded:**
| Name | Artifact Type | Approvers | Roles |
|------|---------------|-----------|-------|
| Plan Approval | plan | 1 | admin, engineer |
| Change Set Approval | changeset | 1 | admin |
| Verification Review | verification | 1 | admin |

**Source:** `packages/workspace/src/types.ts`, `packages/workspace/src/enterprise-storage.ts`

## AuditRecord

```typescript
interface AuditEvent {
  id: string;
  actor: string;
  action: string;
  resource: string;
  details: string;
  timestamp: string;
}
```

**Invariants:**
- Audit records are **append-only** — never modified or deleted.
- Every state transition in the engineering lifecycle produces an audit event.
- The `actor` field identifies the user or agent that performed the action.
- The `action` field uses a consistent verb-noun pattern: `team.created`, `project.created`, `plan.approved`, etc.
- The `timestamp` is ISO-8601 UTC.

**Events generated by default:**
- `team.created`
- `project.created`
- `plan.created`, `plan.approved`, `plan.completed`
- `changeset.created`, `changeset.applied`
- `verification.completed`
- `collaboration.submitted`, `collaboration.approved`, `collaboration.rejected`
- `agent.executed`, `agent.failed`
- `session.created`, `session.completed`

**Source:** `packages/workspace/src/types.ts`, `packages/workspace/src/enterprise-storage.ts`

## Policy Evaluation Flow

```
Request: User attempts to approve artifact of type X
         │
         ▼
Load matching ApprovalPolicy for artifactType = X
         │
         ▼
User role in policy.roles?
   ├── No  → Deny
   └── Yes → Continue
         │
         ▼
Artifact approvals >= policy.requiredApprovers?
   ├── No  → Deny (pending)
   └── Yes → Approved
```

This evaluation model is deterministic, offline-capable, and requires no AI.
