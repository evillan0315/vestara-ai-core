# `@vestara/documentation`

## Overview

`@vestara/documentation` implements Vestara's governed documentation lifecycle.
It inventories Markdown and implementation facts, resolves executable package
requirements, detects drift, plans reviewable work, validates proposals,
produces evidence, and projects documentation state into the Engineering Graph.

Documentation generated by this package is a proposal until deterministic
validation and the applicable approval policy succeed. The package does not
publish directly to a protected branch and does not treat generated prose as
verified truth.

## Responsibilities

This package owns:

- Multi-repository Markdown discovery and classification.
- Documentation authority, status, finding, requirement, plan, proposal, and evidence contracts.
- Executable requirement and standards registries.
- Semantic validation of implementation references, ownership, versions, review freshness, evidence, public APIs, commands, ADR status, kind, and authority.
- Deterministic package, route, command, link, and public-symbol drift detection.
- Documentation impact analysis and dependency-ordered task planning.
- Proposal concurrency checks and authority-aware application policy.
- Baseline-aware CI comparison and decomposable health reporting.
- Documentation event emission and Engineering Graph projection.

It does not own agent orchestration, the event bus, graph persistence, GitHub
publishing, or architectural approval. Those remain with their existing Vestara
owners.

## Architecture

The package is a service composed from deterministic specialists:

```text
DocumentationService
├── DocumentationScanner
│   ├── Markdown parser and classifier
│   ├── Requirement resolver
│   └── Implementation drift extractor
├── DocumentationStandardsRegistry
├── DocumentationImpactAnalyzer
├── DocumentationPlanner
└── Engineering Graph and EventBus adapters
```

`DocumentationService` coordinates lifecycle and state. Specialists own parsing,
requirements, standards, drift, planning, and projection decisions. This follows
Vestara's coordinator-composes-specialists architecture and reuses the existing
EventBus, Engineering Graph contracts, and `VestaraService` lifecycle.

## Lifecycle

`DocumentationService` implements `VestaraService`:

```text
uninitialized → initializing → initialized → starting → running
running → stopping → stopped → disposed
```

`initialize()` restores persisted plans, proposals, and reports. `start()` makes
the service available. `stop()` persists state, and `dispose()` performs the same
safe shutdown before entering the disposed state. Scans and verification are
explicit operations; initialization does not start an uncontrolled background
mutation loop.

## Failure behavior

- Missing repositories produce evidence-backed findings rather than process termination.
- Scan failures set the service's last-failure state and emit `documentation.failed`.
- Invalid or stale proposal checksums reject application as concurrent conflicts.
- Constitutional documents cannot be applied by automation.
- Governance and architecture proposals remain proposal-only and require ADR-governed human handling.
- Unwritable repositories and paths escaping a configured repository root are rejected.
- Proposals that fail deterministic validation cannot be applied.

Failures do not delete source documents or silently downgrade authority policy.

## Health behavior

`health()` reports `healthy` unless a lifecycle operation has recorded a failure,
in which case it reports `degraded` with the failure message. `getStatus()` adds:

- Inventory summary and decomposed documentation health.
- Active plan and task counts.
- Queue depth and pending proposal count.
- Last scan and successful verification timestamps.
- Last failure.

Health is observational; it does not trigger document mutations.

## Security and permissions

- Repository paths are resolved and checked before proposal application.
- High-authority documents cannot bypass proposal and approval policy.
- Constitutional content is permanently blocked from automated application.
- Proposed updates carry a previous checksum to prevent concurrent overwrites.
- Secret-shaped content and machine-specific absolute paths are executable validation failures.
- Provider identity is not embedded in documentation contracts or workflow policy.

Callers remain responsible for authenticating approval actors and supplying only
repositories within their authorized workspace scope.

Explicit owners resolve through package metadata or the repository-local
[approved-owner registry](../../docs/documentation-owners.json).

## Usage

Build the package before consuming its compiled entrypoint:

```bash
pnpm --filter @vestara/documentation build
```

Create and start a service with explicit repository policy:

```ts
import { DocumentationService } from '@vestara/documentation';

const service = new DocumentationService({
  workspaceId: 'workspace-1',
  repositories: [
    {
      id: 'vestara-ai-core',
      path: process.cwd(),
      authority: 'implementation',
      writable: true,
    },
  ],
});

await service.initialize();
await service.start();
const inventory = await service.scan();
const evidence = await service.verify('standard');
await service.dispose();
```

Use `dryRun = true` when running plans unless an approved local application is
explicitly intended.

## Testing

The package tests use temporary real files and the in-process EventBus. They
exercise parsing, inventory, drift, requirements, planning, proposal approval,
concurrency protection, verification evidence, lifecycle events, and
baseline-aware gating.

```bash
bash build-order.sh
pnpm --filter @vestara/documentation test
```

Test evidence: [documentation.test.ts](__tests__/documentation.test.ts).

## Verification

For a package change, run:

```bash
pnpm exec biome check packages/documentation
pnpm --filter @vestara/documentation build
pnpm --filter @vestara/documentation test
pnpm documentation:check
```

The machine-readable documentation report is the verification source. Markdown
and UI views are projections. The `verification-status` in this document refers
to the package build and deterministic test evidence above; it does not claim
that remote CI has passed before a real workflow run succeeds.

## Ownership

| Concern | Owner |
|---------|-------|
| Package implementation | Documentation Automation maintainers |
| Executable requirements and standards | Standards Agent with human review |
| Architecture changes | ADR governance and human approvers |
| Proposal approval identity | Calling Workspace/API permission layer |
| Graph and event persistence | Existing Engineering Graph and Event Store owners |

Changes to the canonical public-package README contract require updating
`PUBLIC_PACKAGE_README_SECTIONS`, `PUBLIC_PACKAGE_README_FRONTMATTER`, fixtures,
and tests in the same change.

## Related ADRs

- [ADR-001 — Runtime](../../docs/ADR/ADR-001-runtime.md) defines the runtime lifecycle boundary. This package implements a `VestaraService`; it must not be presented as a managed Runtime unless it adopts the full Runtime contract.

No ADR currently delegates constitutional, governance, or architecture mutation
authority to this package.
